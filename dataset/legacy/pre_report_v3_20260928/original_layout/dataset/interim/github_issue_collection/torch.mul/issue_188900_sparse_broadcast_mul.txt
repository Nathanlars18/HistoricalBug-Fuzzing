Description:

🐛 Describe the bug

When two tensors are multiplied elementwise and the operand whose size-1 dimension must be broadcast up is a sparse COO tensor, torch.mul silently returns an incorrect result: only the index == 0 slice along the broadcast dimension is populated, and all other slices are zero.

Broadcasting works correctly in every other direction (dense operand broadcast up against a full sparse tensor, equal shapes, scalar multiply). The bug is specific to expanding a singleton dimension of the sparse operand.

No error or warning is raised.


Minimal reproducer:

```python
import torch

s = torch.tensor([[1., 2.], [3., 4.]]).to_sparse_coo()

# sparse tensor with trailing singleton dimension
s1 = s[:, :, None]

# dense tensor which broadcasts the singleton dimension
d = torch.ones(1, 1, 3)

out = (s1 * d).to_dense()

expected = s.to_dense()[:, :, None] * d

print(out)
print(expected)

print("max abs err:", (out - expected).abs().max().item())
Output:
max abs err: 4.0
The output along the first broadcast slice is correct:
out[...,0] == expected[...,0]
However:
out[...,1:]
is entirely zero.
The expected behavior is that broadcasting should replicate the sparse values along the expanded dimension.
Expected Behavior:
Either:
1. Broadcast the sparse operand's singleton dimension correctly.
The sparse values should be replicated across the expanded dimension according to dense broadcasting semantics.
or:
2. Raise an explicit error if this sparse broadcasting pattern is unsupported.
The current behavior silently returns an incorrect tensor.
Real-world Impact:
The bug was found while writing an MTTKRP kernel involving sparse tensors:
torch.sum(
    B[:, :, :, None]
    * D[None, None, :, :]
    * C[None, :, None, :],
    axis=(1, 2)
)
where:
- B is a sparse COO tensor.
- B[:, :, :, None] introduces a singleton rank dimension.
- The singleton dimension should broadcast against dense factor matrices.
The result was silently incorrect:
- the first rank column was correct.
- all remaining rank columns were zero.
No warning or error indicated that the computation was wrong.

Technical Discussion:
leninathikam investigated the issue and identified the root cause.
The problem occurs in:
intersection_binary_op_sparse_dense_out
inside:
SparseTensorMath.cpp
Current behavior:
The sparse-dense multiplication path supports broadcasting when the dense tensor expands against a sparse tensor.
However, when the sparse operand itself contains a size-1 dimension that needs broadcasting, the implementation does not explicitly expand the sparse tensor.
As a result:
- sparse indices are used directly.
- only index == 0 along the broadcast dimension receives values.
- remaining broadcast slices stay zero.
Root Cause:
The sparse multiplication path is missing explicit sparse broadcasting.
The sparse operand should first be expanded using:
at::sparse_broadcast_to
before performing the intersection operation.
Proposed Fix:
Before sparse-dense intersection:
1. Infer the broadcasted size.
2. Apply:
at::sparse_broadcast_to
to the sparse operand.
3. Continue with the existing multiplication logic.
Regression tests should cover:
- singleton sparse dimensions
- sparse/dense broadcasting
- MTTKRP-style workloads
