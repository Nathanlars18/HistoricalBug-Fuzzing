# API Profile Schema v1.3

## 1. Purpose

An API Profile is a version-pinned, evidence-backed description of one API
target used by the Harness synthesis pipeline.

It records the Python API contract, the selected execution binding,
documented validity constraints, FlashFuzz support, and API-level validation.
Knowledge selection, strategy planning, Harness generation, execution results,
and feedback decisions are outside this schema.

---

## 2. Core Invariants

New records use schema_version `1.3`. Version 1.0 through 1.2 records remain readable
unchanged. An index tensor has normalized type `tensor` and semantic role
`index_tensor`.
In v1.2 and later, `constraint_property` records what is constrained and
`constraint_scope` records how many contract elements participate.
`constraint_kind` is retained only as a compatibility/indexing field for older
consumers; it is not a defect taxonomy.

One profile represents one combination of:

- framework version and commit;
- Python API and callable variant;
- execution route and, where applicable, C++ or ATen overload;
- backend scope.

Changing any item above creates a new `profile_id`. Correcting or enriching the
same target creates a new `revision` under the existing `profile_id`.

Every asserted API fact has supporting `evidence_refs`. Missing, unknown, and
conflicting information remains explicit and is not replaced by guessed values.

Profiles with `target_binding.status = unresolved` or a blocking Validation Issue
are retained for traceability but are not eligible HarnessSpec inputs. Resolving
them creates a new revision; the API Profile never delegates binding guesses to
the Harness generator.

## 4. `metadata`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `parent_revision_ref` | Profile Revision Reference or null | yes | Direct predecessor of this revision |
| `generated_at` | timestamp | yes | Materialization time |
| `builder_version` | string | yes | Deterministic Profile Builder version |
| `content_hash` | string | yes | SHA-256 of canonical profile content |

### 4.1 Profile Revision Reference

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `profile_id` | string | yes | Referenced profile identifier |
| `revision` | positive integer | yes | Referenced revision |
| `content_hash` | string | yes | Hash of the referenced revision |

Revision 1 has `parent_revision_ref = null`. A later revision references the
direct preceding retained revision with the same `profile_id` and a lower
revision number. The API Profile index resolves the reference; file paths are
not stored in it. The resolved hash must match, and ancestry must be acyclic.

The Builder computes `content_hash` from canonical JSON with the
`metadata.content_hash` value omitted from the hash input.

A revision becomes immutable after registration in the API Profile index. The
index stores the active revision and optional retirement state. Superseding or
retiring a profile never changes an existing revision or its hash.

All fields in this section, plus `profile_id` and `revision`, are Builder-owned
and are not generated by an LLM.

## 5. `target`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `framework` | string | yes | Framework name |
| `framework_version` | string | yes | Exact release |
| `framework_commit` | string | yes | Exact 40- or 64-character Git object ID |
| `backend_scope` | array of enums | yes | `cpu`, `cuda`, `mps`, or `other` |
| `python_api` | string | yes | Fully qualified Python API |
| `callable_kind` | enum | yes | `function`, `tensor_method`, `module_function`, `operator`, `constructor`, or `other` |
| `python_variant` | string | yes | Stable name for the Python-facing variant |
| `aliases` | array of strings | yes | Verified aliases; empty when none are known |

`python_variant` does not replace the exact overload recorded in
`target_binding`.


Git commit fields accept full 40-character SHA-1 or 64-character SHA-256 object
IDs. Profile and evidence content hashes remain 64-character SHA-256 values.

## 6. `python_contract`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `documentation_status` | enum | yes | `available`, `partial`, `missing`, or `conflicting` |
| `coverage` | Coverage object | yes in v1.2 | Per-component collection coverage; prevents empty arrays from being misread as exhaustive |
| `signature` | string or null | yes | Normalized Python signature |
| `behavior_summary` | string or null | yes | Concise documented behavior |
| `parameters` | array of Parameter objects | yes | Ordered Python parameters |
| `returns` | array of Return objects | yes | Documented return values |
| `documented_domains` | array of Domain objects | yes | Explicitly documented domains |
| `documented_exceptions` | array of Exception objects | yes | Documented expected exceptions |
| `evidence_refs` | array of Evidence IDs | yes | Evidence for signature and overall behavior |

The summary does not introduce historical Bug triggers or fuzzing strategies.

`coverage.signature`, `coverage.parameters`, and `coverage.returns` use
`complete`, `partial`, `missing`, or `conflicting`. `coverage.domains`,
`coverage.exceptions`, `coverage.constraints`, and `coverage.effects` use
`not_collected`, `partial`, `reviewed_no_explicit_items`,
`reviewed_with_items`, or `conflicting`. `not_collected` means unknown, not
unrestricted and not known-empty.

### 6.1 Parameter Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `parameter_id` | string | yes | Profile-local stable identifier |
| `name` | string | yes | Python parameter name |
| `ordinal` | non-negative integer or null | yes | Positional order when applicable |
| `parameter_kind` | enum | yes | `positional_only`, `positional_or_keyword`, `keyword_only`, `variadic_positional`, or `variadic_keyword` |
| `required` | boolean | yes | Whether the caller must supply it |
| `documented_type` | string or null | yes | Target-version documented type |
| `normalized_types` | array of enums | yes | Normalized accepted type categories |
| `default` | Default Value object | yes | Default-value semantics |
| `semantic_role` | enum | yes | Role in the API contract |
| `normalization_basis` | enum | yes | `source_explicit`, `deterministic`, `manual_interpretation`, or `unknown` |
| `constraint_refs` | array of Constraint IDs | yes | Applicable constraints |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

Allowed `normalized_types` values:

```text
tensor, tensor_sequence, scalar, integer, floating, boolean,
string, dtype, device, layout, memory_format, shape, dimension, generator,
callable, object, none, unknown, other
```

Allowed `semantic_role` values:

```text
input_tensor, other_tensor, index_tensor, output_tensor, bias_tensor,
dimension_selector, shape, dtype, device, layout, memory_format, scalar,
boolean_flag, sequence, generator, configuration, unknown, other
```

`manual_interpretation` describes normalization, not evidence. Such a value
still requires source evidence and human review.

### 6.2 Default Value Object

| Field | Type | Required | Description |

| `kind` | enum | yes | `no_default`, `literal`, `none_literal`, `runtime_defined`, or `unknown` |
| `value` | JSON value or null | yes | Literal default when representable |

`value` is non-null only for `literal`. A non-JSON literal may use its original
string spelling.

### 6.4 Domain Object

| Field | Type | Required | Description |

| `domain_kind` | enum | yes | `dtype`, `device`, `layout`, `memory_format`, `gradient_mode`, or `other` |

### 6.5 Exception Object

| `description` | string or null | yes | Additional documented behavior |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

## 7. `target_binding`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `binding_kind` | enum | yes in v1.2 | `aten_operator`, `python_callable`, or `none` |
| `status` | enum | yes | `resolved`, `partial`, `unresolved`, `conflicting`, or `not_applicable` |
| `operator_name` | string or null | yes | Base C++ or ATen operator |
| `operator_overload` | string or null | yes | Exact overload; use `default` for an unnamed default overload |
| `operator_schema` | string or null | yes | Exact target-version schema |
| `cpp_callable` | string or null | yes | C++ callable used by the Harness |
| `binding_parameters` | array of Binding Parameter objects | yes | Structured binding parameters |
| `argument_mapping` | array of Argument Mapping objects | yes | Python-to-binding mapping |
| `parameter_dispositions` | array of Parameter Disposition objects | yes in v1.2 | Exhaustive accounting for every Python parameter |
| `return_mapping` | array of Return Mapping objects | yes | Binding-to-Python return mapping |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

For `aten_operator`, `resolved` identifies one overload. For `python_callable`,
`resolved` means the Python callable and its structured contract are identified;
it does not imply that the current C++ Harness can execute it. Compilation and
reachability remain separate validation results.

### 7.1 Binding Parameter Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `binding_parameter_id` | string | yes | Profile-local identifier |
| `name` | string | yes | Operator-schema parameter name |
| `ordinal` | non-negative integer | yes | Schema order |
| `schema_type` | string | yes | Exact operator-schema type |
| `default` | string or null | yes | Original schema default |

### 7.2 Argument Mapping Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `python_parameter_ref` | Parameter ID or null | yes | Source Python parameter |
| `source_parameter_refs` | array of Parameter IDs | yes in v1.3 | Every Python parameter used by the binding expression; empty only for source-free mappings |
| `binding_parameter_ref` | Binding Parameter ID | yes | Destination binding parameter |
| `mapping_kind` | enum | yes | `direct`, `renamed`, `default_injected`, `converted`, `packed`, `omitted`, or `unresolved` |
| `transformation` | string or null | yes | Concise transformation when needed |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

This records a semantic mapping, not C++ code or a Helper invocation.
`renamed`, `converted`, and `packed` require wrapper-source evidence. A
multi-parameter or conditional expression uses `source_parameter_refs` to name
all participating Python parameters and preserves the complete expression in
`transformation`. Positional fallback guessing is prohibited. Each Python parameter is also classified as `mapped`,
`converted`, `consumed_by_wrapper`, `default_only`,
`not_applicable_to_binding`, or `unresolved` in `parameter_dispositions`.

### 7.3 Return Mapping Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `binding_return_position` | non-negative integer | yes | Position in the binding result |
| `python_return_ref` | Return ID or null | yes | Corresponding Python return |
| `mapping_kind` | enum | yes | `direct`, `converted`, `packed`, `unpacked`, `omitted`, or `unresolved` |
| `description` | string or null | yes | Concise mapping description |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

## 8. `documented_constraints`

This array contains atomic API-validity requirements supported by
target-version documentation, operator schemas, or versioned source code.
Historical Bug risks and exploration goals are excluded.

### 8.1 Constraint Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `constraint_id` | string | yes | Profile-local stable identifier |
| `constraint_kind` | enum | yes | Legacy indexing tag retained for v1.0-v1.1 compatibility |
| `constraint_property` | enum | yes in v1.2 | `type`, `structure`, `dtype`, `shape`, `rank`, `value`, `device`, `layout`, `memory_format`, `gradient_mode`, `output`, `environment`, or `other` |
| `constraint_scope` | enum | yes in v1.2 | `single_parameter`, `cross_parameter`, `return_value`, or `call_environment` |
| `applies_to` | array of local references | yes | Affected profile elements |
| `condition` | string or null | yes | Applicability condition |
| `requirement` | string | yes | One atomic validity requirement |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence |

Runtime observations remain in validation or experiment results. Machine
predicates may be introduced only after their representation is defined in a
later schema version.

`constraint_property` and `constraint_scope` are orthogonal: for example, a
same-shape requirement is `property = shape` and `scope = cross_parameter`.

### 8.2 Effect Object

An Effect records one source-backed `mutates_parameter`, `aliases_parameter`,
`writes_output_parameter`, `global_state`, `unknown`, or `other` behavior. An
empty array with `coverage.effects = not_collected` is not a no-effects claim.

## 9. `flashfuzz_support`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `flashfuzz_commit` | string | yes | Exact 40- or 64-character inspected Git object ID |
| `api_list_status` | enum | yes | `listed`, `unlisted`, or `unknown` |
| `evidence_refs` | array of Evidence IDs | yes | Supporting API-list evidence |

This object records only whether the Python API appears in the pinned FlashFuzz
API list. `listed` does not assert that a Harness compiles or reaches the target;
`unlisted` does not assert that the API is untestable. Binding evidence belongs
to `target_binding`, general construction capability belongs to the Helper
Capability Profile, and executable support is established by Validation checks.

## 10. `validation`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `validation_status` | enum | yes | `not_run`, `partial`, `passed`, or `failed` |
| `execution_readiness` | enum | yes | `unassessed`, `ready`, `needs_adapter`, `review_required`, or `blocked` |
| `checks` | array of Validation Check objects | yes | Deterministic check results |
| `issues` | array of Validation Issue objects | yes | Blocking and non-blocking issues |

The Validator derives both status fields from checks and issues. They are not
selected by an LLM or assigned manually without corresponding evidence.

`ready` covers API-level binding, compilation, smoke execution, and target
reachability. It does not assert that a Knowledge item or Helper strategy is
implementable.

### 10.1 Validation Check Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `check_id` | string | yes | Profile-local identifier |
| `check_kind` | enum | yes | `python_resolution`, `signature_resolution`, `operator_schema_resolution`, `argument_mapping`, `return_mapping`, `cpp_binding_resolution`, `cpp_compile`, `cpp_smoke_execution`, or `target_reachability` |
| `backend` | enum or null | yes | Backend used by the check |
| `status` | enum | yes | `not_run`, `passed`, `failed`, `blocked`, or `not_applicable` |
| `summary` | string | yes | Concise result summary |
| `evidence_refs` | array of Evidence IDs | yes | Logs, traces, or source evidence |

`not_run` is distinct from `failed`.

### 10.2 Validation Issue Object

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `issue_id` | string | yes | Profile-local identifier |
| `issue_kind` | enum | yes | Normalized issue category |
| `blocking` | boolean | yes | Whether it prevents API-level execution |
| `description` | string | yes | Concise issue description |
| `affected_refs` | array of local references | yes | Affected profile elements |
| `evidence_refs` | array of Evidence IDs | yes | Supporting evidence; empty only if not yet available |

Allowed `issue_kind` values:

```text
missing_documentation, documentation_conflict, signature_ambiguity,
overload_ambiguity, binding_unresolved, argument_mapping_unresolved,
return_mapping_unresolved,
flashfuzz_support_gap, compile_failure, runtime_failure,
reachability_unconfirmed, version_mismatch, other
```

A separate deterministic policy defines the complete mapping from checks and
issues to the two top-level validation states. A correct Python-only Profile may
have `validation_status = passed` and `execution_readiness = needs_adapter`.
It is not eligible for the current C++ Harness route.

## 11. `evidence`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `evidence_id` | string | yes | Profile-local stable identifier |
| `source_kind` | enum | yes | Evidence source category |
| `source_location` | string | yes | Local artifact path or official URL |
| `source_revision` | string or null | yes | Source version, tag, or commit |
| `locator` | string or null | yes | Symbol, schema, line, or document section |
| `content_hash` | string or null | yes | Hash of captured source content |
| `excerpt` | string or null | yes | Supporting excerpt of at most 1,000 Unicode characters |
| `collected_at` | timestamp | yes | Collection time |

Allowed `source_kind` values:

```text
runtime_signature, runtime_docstring, official_documentation, operator_schema,
python_wrapper_source, pytorch_source, flashfuzz_api_list, flashfuzz_source,
validation_case, build_log, runtime_trace
```

Longer source content remains external and is addressed by `source_location`,
`locator`, and `content_hash`. `excerpt = null` is permitted for binary or
generated evidence and when the locator is sufficient.

Mutable external content should be captured or hashed. If this is unavailable,
`content_hash = null` and the limitation is recorded as a Validation Issue.

## 12. `review`

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `review_status` | enum | yes | `unreviewed`, `in_review`, `approved`, or `needs_revision` |
| `reviewer` | string or null | yes | Reviewer identifier |
| `reviewed_at` | timestamp or null | yes | Review completion time |
| `issue_refs` | array of Validation Issue IDs | yes | Issues retained or identified during review |

Automatic results belong to `validation`. Human review does not replace source
evidence or deterministic checks.

Runtime promotion leaves the Profile `unreviewed`. A separate review operation
creates a new revision. Review follows `api_profile_human_review_rules.md`;
reviewers report evidence or mapping defects and do not directly edit generated
JSON. `approved` means the recorded assertions faithfully match the cited
evidence; it does not mean exhaustive documentation coverage or current-Harness
execution readiness.

## 13. Common Value Semantics

The Profile distinguishes known-empty, not-applicable, not-documented,
not-yet-checked, unknown, and conflicting states.

For v1.2 collection fields, interpret an empty array together with its explicit
coverage state. `not_collected` is unknown; `reviewed_no_explicit_items` is the
known-empty state. `null` is used only where the field permits unavailable or inapplicable
scalar content. An empty string is not a substitute for `null`. A factual
non-null value normally has at least one evidence reference; an explicitly
missing or unresolved state may temporarily have none.

Core identity, target selection, references, and hashes are strict. Incomplete
documentation and non-critical unknown values are allowed when represented
explicitly and carried into validation or review.

Free text remains concise and evidence-backed. Except for the 1,000-character
Evidence excerpt limit, this schema does not impose arbitrary hard text limits.
The machine-readable JSON Schema may add conservative technical limits where
needed for safe processing.
